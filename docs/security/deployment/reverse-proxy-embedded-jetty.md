# jCustos on embedded Jetty 12 behind a reverse proxy

Status: 00.84.00 · CWE-614 (Sensitive Cookie Without 'Secure'), CWE-1004 (Sensitive Cookie Without
'HttpOnly'), CWE-200 (Exposure of Sensitive Information), CWE-352, CWE-778

This page is the checklist for the common production set-up: the application runs an embedded
Jetty 12 (`jetty-ee11`), a reverse proxy such as Caddy or nginx terminates TLS in front of it, and
the hop from the proxy to Jetty is plain HTTP on loopback. How the client address survives that hop
is described in [reverse-proxy.md](reverse-proxy.md); this page covers the rest: the session cookie,
the server banner, browser-callable Vaadin methods, the request id, the address limit of the login
throttle and the origin guard.

All Jetty method names below were checked against Jetty 12.1.15, the version the build pins.

## 1. Bind the connector to loopback

Only the proxy may reach Jetty. Everything else on this page assumes that a client cannot talk to
the connector directly.

```java
Server server = new Server();
HttpConfiguration http = new HttpConfiguration();
http.setSendServerVersion(false);   // section 3
http.setSendXPoweredBy(false);
ServerConnector connector = new ServerConnector(server, new HttpConnectionFactory(http));
connector.setHost("127.0.0.1");
connector.setPort(8080);
server.addConnector(connector);
```

## 2. Session cookie attributes

None of the three security attributes is a Jetty default:

| Attribute | Jetty 12 default | Set it with |
|---|---|---|
| `HttpOnly` | off | `sessionHandler.setHttpOnly(true)` |
| `Secure` | only when the request reached Jetty over TLS (`setSecureRequestOnly(true)`) | `sessionHandler.setSecureCookies(true)` |
| `SameSite` | not sent | `sessionHandler.setSameSite(HttpCookie.SameSite.LAX)` |

The `Secure` row is the trap. `setSecureRequestOnly(true)` marks the cookie secure only when the
connection to Jetty is secure. Behind a proxy that terminates TLS the connection to Jetty is plain
HTTP, so the cookie goes out **without** `Secure`, and a browser sends it over any later plain-HTTP
request to the same host. `setSecureCookies(true)` sets the attribute on every response.

Give the cookie an application-specific name as well. Cookies are stored per host, not per port;
two applications on one host that both use `JSESSIONID` overwrite each other's session without an
error message.

```java
ServletContextHandler context = new ServletContextHandler(ServletContextHandler.SESSIONS);
SessionHandler sessions = context.getSessionHandler();   // org.eclipse.jetty.ee11.servlet
sessions.setSessionCookie("MYAPP_SESSION");
sessions.setHttpOnly(true);
sessions.setSecureCookies(true);
sessions.setSameSite(HttpCookie.SameSite.LAX);           // org.eclipse.jetty.http.HttpCookie
```

A WAR with a `web.xml` sets the same through `<session-config><cookie-config>`; every Vaadin demo
of this repository does, and `docs/dx/5-minute-setup-vaadin.md` (section 3) shows the block.
Verify the result on the public URL:

```
curl -sI https://app.example/ | grep -i set-cookie
# Set-Cookie: MYAPP_SESSION=…; Path=/; Secure; HttpOnly; SameSite=Lax
```

Some browsers discard a `Secure` cookie on `http://localhost`; during local development without
TLS, test against `https://` or accept that the session cookie is dropped.

## 3. No server banner

Jetty announces itself in a `Server` header unless told otherwise:
`HttpConfiguration.setSendServerVersion(false)` (section 1). Caddy adds its own `Server: Caddy`
and passes the upstream's header through; remove both:

```caddyfile
app.example {
    header -Server
    reverse_proxy 127.0.0.1:8080 {
        header_down -Server
    }
}
```

nginx: `server_tokens off;` and `proxy_hide_header Server;`.

The banner is no vulnerability in itself, but it tells an attacker which advisories to try first.

## 4. `@ClientCallable` methods are public endpoints

A Vaadin method annotated with `@ClientCallable` can be called by any script running in the page,
with any arguments, as often as the caller likes, as long as the component is attached. Route
access checks (`@RequiresPermission` or an application's own restriction annotation on the view) do
not run again for such a call.

- Treat every argument as untrusted input: validate type, range and length.
- Call only services that enforce their own authorisation: a `@Secured` wrapper generated by the
  annotation processor, or a method that starts with `JCustosEnforcer.requirePermission(...)` /
  `requireRole(...)`. Never decide on the client's word that an action is allowed.
- Do not expose a `@ClientCallable` on a component that a denied user can still reach.

## 5. Request id for audit correlation (R5)

Audit records and audit lines carry the correlation id of the request (`corr=` in the line). jCustos
takes the `X-Request-ID` header **only** from a peer that the registered `ClientAddressResolver`
trusts (the proxy of section 1 in [reverse-proxy.md](reverse-proxy.md)), only from a single header
line and only in the format `[A-Za-z0-9._:-]{1,128}`. Every other request gets a server-side UUID.
Let the proxy set the header and **replace** whatever the client sent:

```caddyfile
reverse_proxy 127.0.0.1:8080 {
    header_up X-Request-ID {http.request.uuid}
}
```

nginx: `proxy_set_header X-Request-ID $request_id;`.

```java
VaadinSecurity.bootstrap()
    .clientAddress(ClientAddressResolver.trustedProxies("127.0.0.1", "::1"))
    // optional, a different header name:
    // .correlationIds(new TrustedPeerCorrelationIdResolver(
    //     ClientAddressResolver.trustedProxies("127.0.0.1", "::1"), "X-Correlation-ID"))
    .install();
```

The proxy then logs the same id in its access log, and one grep finds the request on both sides.

## 6. Address limit of the login throttle (R3)

`LoginAttemptLimits.withAddressLimit(...)` adds a counter per client address to the login policy,
against an attacker who tries a few passwords on many accounts from one address. It is off by
default. Behind a proxy it **requires** the trusted-peer resolver of
[reverse-proxy.md](reverse-proxy.md): without it every client shares the proxy's address, and the
first sprayer locks everybody out.

```java
LoginAttemptLimits limits = LoginAttemptLimits.defaults()
    .withAddressLimit(new LoginAttemptLimits.AddressLimit(
        50, Duration.ofMinutes(15), Duration.ofMinutes(1), Duration.ofHours(1)))
    .withMaxConcurrentCredentialChecks(16);   // credential-check gate, JS-SEC-063
VaadinSecurity.bootstrap()
    .clientAddress(ClientAddressResolver.trustedProxies("127.0.0.1", "::1"))
    .bruteForce(new InMemoryLoginAttemptPolicy(limits, Clock.systemUTC(), auditService))
    .install();
```

Choose the threshold with the clients in mind that legitimately share one address: an office
behind one NAT, a mobile carrier's gateway.

## 7. Origin guard for cookie-based REST sessions (CSRF)

A REST API whose session rides on a cookie needs protection against cross-site requests; one that
expects a bearer token does not. `RestOriginGuard` refuses a state-changing request whose
`Sec-Fetch-Site` and `Origin` show a foreign origin. It compares against the `Host` header, so the
proxy must pass the public host through (Caddy does by default; nginx needs
`proxy_set_header Host $host;`). If the proxy rewrites `Host`, list the public origin explicitly:

```java
RestSecurity.bootstrap()
    .originGuard(RestOriginGuard.sameOrigin()
        .withAllowedOrigins(Set.of("https://app.example")))
    .install();
```

The allowlist replaces the `Host` comparison; include every credentialed CORS origin as well.
`docs/security/csrf.md` describes what the guard does and does not cover.

## 8. Checklist

- [ ] Connector bound to `127.0.0.1`; the port is not reachable from outside.
- [ ] `Set-Cookie` on the public URL shows the application's own name, `Secure`, `HttpOnly`,
      `SameSite=Lax`.
- [ ] No `Server` header on the public URL (`curl -sI https://app.example/ | grep -i '^server'`
      prints nothing).
- [ ] Trusted proxies registered; a forged `X-Forwarded-For` from outside does not appear in audit
      lines ([reverse-proxy.md](reverse-proxy.md), "Verifying a deployment").
- [ ] The proxy sets `X-Request-ID`; audit lines end with `corr=` and the id appears in the proxy
      log.
- [ ] Every `@ClientCallable` validates its arguments and calls only enforced services.
- [ ] Cookie-based REST sessions: origin guard installed; a cross-origin `POST` is answered with
      `403`.
